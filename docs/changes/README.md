# Change pipeline

Every change goes through five roles, in this order. Each role is a Claude Code
subagent in `.claude/agents/`, and `/change` (`.claude/commands/change.md`) runs
them one after another.

| Step | Role | Agent | Writes | Never does |
| --- | --- | --- | --- | --- |
| 1 | Senior architect | `architect` | `plan.md` | Edit code, tests, migrations or workflows |
| 2 | Senior quality engineer and software architect | `plan-reviewer` | `plan-review.md` | Rewrite the plan |
| 3 | Technical lead, gate 1 | `tech-lead` | `plan-approval.md` | Approve a plan the reviewer has not passed |
| 4 | Senior software developer | `developer` | Code, tests, `implementation.md` | Go beyond the approved plan |
| 5 | Senior tester and security engineer | `tester` | `test-report.md` | Fix anything |
| 6 | Technical lead, gate 2 | `tech-lead` | `delivery-approval.md` | Approve without a passing test report |

After step 6 the pipeline stops for the owner. A tech-lead approval is a role in
this pipeline; it is never the owner's confirmation that `AGENTS.md` requires,
and it never counts as an owner decision under P-7.

## Where the records live

One folder per change: `docs/changes/<id>/`. The id is the plan item it closes
(`GAP-01`, `ISO-2`, `ADM-06`), or a short kebab-case name when there is none.
Several items in one change use the first id and list the rest in the plan.

```
docs/changes/<id>/
  plan.md               architect
  plan-review.md        plan-reviewer (one "Round N" section per review)
  plan-approval.md      tech-lead, gate 1
  implementation.md     developer
  test-report.md        tester (one "Round N" section per test run)
  delivery-approval.md  tech-lead, gate 2
```

These files are committed on the change branch with the code, so the pull
request carries its own plan, reviews and evidence.

## Verdict lines

Every review and approval file ends with exactly one verdict line, which
`/change` reads to decide the next step:

- `Verdict: APPROVED`
- `Verdict: CHANGES NEEDED`
- `Verdict: BLOCKED ON OWNER` (an owner decision, exception or behaviour change is
  needed; the file names it, for example O-11)

## Loops

- A plan sent back goes to the architect, then to the reviewer again. A third
  rejection stops the pipeline and goes to the owner.
- A failed test report or a rejected delivery goes back to the developer, then to
  the tester again. A third failure stops the pipeline and goes to the owner.
- If the developer finds the plan cannot be followed, the developer stops and the
  change goes back to step 1. The developer never changes the plan.

## Rules every role follows

- Read `AGENTS.md` (or `CLAUDE.md`, its copy), `ENGINEERING_STANDARDS.md`,
  `docs/PROJECT_PROFILE.md` and `docs/quality/refinement-plan-2026-10-28.md`
  before starting. Where two of them disagree, the stricter rule applies.
- Evidence, not claims (P-8). Every check is quoted as run: command, exit code and
  the relevant output lines. Anything not run is written NOT RUN with the reason
  and the CI job that covers it.
- Only the owner decides exceptions and behaviour changes (P-7). Quote the owner's
  exact words with the date and where they were given; never paraphrase, never
  invent one. Without the owner's words the verdict is BLOCKED ON OWNER.
- Never weaken a gate, guard or test to make something pass (P-6).
- Never commit to `rebuild/dotnet-platform`, `main`, `release/v1` or
  `feature/interviewer-portal`, and never modify DH-WEBSITE-main.
- Never write to `DigitalHubContent`. Integration tests use
  `DigitalHubContent_Test`; end-to-end uses `DigitalHubContent_E2e`, reset first.
- Show every migration before it is applied, with the elevated account only.
- Run .NET tests in Release.
- Secrets stay in dotnet user-secrets: never printed, logged or committed.
- Never stop a process you did not start. Claude Code uses ports 42xx.

## Track checklists

Each plan names its track, and both the architect and the tester apply that
track's checklist.

**G1, Wave 0 (security, GAP-01 to GAP-03).** `npm audit --audit-level=high` on the
full tree, production and development, reports 0 in the website and the Studio.
Fixed entries are removed from `.github/security/known-findings.json`. Each
remaining advisory cites a D-NNN entry in `docs/deferred-items.md` with the
owner's quote and an expiry. Tests, design check, build and section comparison
are green, and the screenshot report is reviewed by hand. Lockfiles are
regenerated by npm, never hand-edited (B-7). A `github-actions` bump updates its
golden copy in `.github/security/`.

**G1, Waves 1 to 3 (gates and API).** One gate per pull request (B-8). A new gate
reports for seven days through a `*_BLOCKING_FROM` date, then blocks; a gate that
replaces existing protection blocks at once. Every gate has a committed canary
fixture it must reject (GAP-21). Actions are pinned by 40-character SHA, the SQL
Server image by digest, Node and .NET exactly. Baselines only shrink.

**G2, isolation (ISO-1 to ISO-6, ADR 0001).** Follow `docs/adr/0001-split-public-forms-api.md`.
ISO-1 changes no behaviour: all 208 integration and 22 end-to-end tests pass
unchanged. The public API answers only the two form routes, and a test proves
every other path returns 404. The `dh_public_forms` login is proven unable to
read users, roles, sessions or audit, or to change content. ISO-4 merges only
after ISO-5.

**G3, admin functions (ADM-01 to ADM-25).** The finding, its evidence and its fix
come from `docs/quality/admin-audit-2026-10-28.md`. The regression test is
committed and shown failing before the fix. The end-to-end suite gets a test for
each Major. A Minor that is not fixed becomes a D-NNN entry with an expiry.

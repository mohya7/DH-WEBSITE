## 3. Design

### 3.1 Approach

One new job in `ci.yml`, `website-browser`, that builds both variants one after the
other and runs the unchanged Playwright suite against each, then a committed
checker reads both Playwright JSON reports and decides.

**Job `website-browser`** ("Website — browser tests, default and consent builds"),
appended after `screenshot-parity`:

- `runs-on: ubuntu-24.04` (same reason as PR #38). No `needs:`, no `if:`, no
  `continue-on-error` anywhere in the job. Runs on every `pull_request` event and
  every push to `rebuild/dotnet-platform`, through the existing triggers.
- Job `env`: `BROWSER_TESTS_BLOCKING_FROM: "<YYYY-MM-DD>"` (3.3),
  `CONTENT_SOURCE: snapshot`, `PUBLIC_SITE_URL: https://digitalhub.com.eg`,
  `PLAYWRIGHT_HTML_OPEN: never`. `defaults.run.working-directory: website`.
- Steps:
  1. `actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4.4.0` (the SHA
     GAP-08 uses; `git ls-remote` today: `refs/tags/v4` = that SHA).
  2. `actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4.4.0`
     (`refs/tags/v4` = `refs/tags/v4.4.0` = that SHA), `node-version:
     ${{ env.NODE_VERSION }}`, `cache: npm`, `cache-dependency-path:
     website/package-lock.json`.
  3. `npm ci`.
  4. **Canary** — `node tools/browser-suite/run-canary.mjs` (3.4). Always blocking.
  5. `npx playwright install --with-deps chromium` (as the Studio job).
  6. **Default build** — `npm run build`.
  7. **Browser tests, default build** — env `PLAYWRIGHT_JSON_OUTPUT_NAME:
     ${{ github.workspace }}/reports/website-browser/default.json`,
     `PLAYWRIGHT_HTML_OUTPUT_DIR: ${{ github.workspace }}/reports/website-browser/default-html`;
     run:
     ```bash
     status=0
     npx playwright test --reporter=list,json,html --output "${{ github.workspace }}/reports/website-browser/default-results" || status=$?
     echo "Playwright exit ${status}"
     # 1 is failed tests, which the check step judges; any other code means the run itself broke.
     if [ "${status}" -gt 1 ]; then exit "${status}"; fi
     ```
  8. **Consent build** — env `SNAPSHOT_SETTINGS_FIXTURE: consent`;
     run `rm -rf out` then `npm run build` (a clean `out/`, so nothing from the
     default build is left over).
  9. **Browser tests, consent build** — as step 7 with `consent` in the three paths.
  10. **Check both runs** — `node tools/browser-suite/check-report.mjs
      tools/browser-suite/expected.json
      "default=${{ github.workspace }}/reports/website-browser/default.json"
      "consent=${{ github.workspace }}/reports/website-browser/consent.json"`.
      Writes a table to `$GITHUB_STEP_SUMMARY` when that variable is set.
  11. **Upload** — `actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02 # v4.6.2`
      (`refs/tags/v4` = `v4.6.2` = that SHA), `if: always()`, name
      `website-browser-report`, path `reports/website-browser`,
      `if-no-files-found: warn`. (`if: always()` on the upload only; the
      "no `if:`" rule above is about the gate steps.)

No inline `node -e` or `--input-type` (the security self-test,
`.github/security/gate.test.mjs:1081-1090`, fails on inline interpreters in any
workflow). Every shell variable is quoted for shellcheck.

**Checker `website/tools/browser-suite/check-report.mjs`** (Node built-ins only).
Usage: `check-report.mjs <expected.json> default=<report> consent=<report>`.
Reads `BROWSER_TESTS_BLOCKING_FROM`. Exit 0 pass (or report-mode failures), 1 fail,
2 wrong arguments.

`website/tools/browser-suite/expected.json`:

```json
{
  "minimumTests": 29,
  "builds": {
    "default": { "skippedFiles": ["consent.spec.ts"], "skippedTests": [] },
    "consent": { "skippedFiles": [], "skippedTests": [{ "file": "pages.spec.ts", "title": "nothing from Tag Manager loads when the container id is empty" }] }
  }
}
```

A test's id is `<file> › <describe titles…> › <title>` from the JSON
(`suites` walked recursively). Rules, each with a test (5.1):

- **Fails at once, in report mode too** (the gate cannot see, P-5, "a gate that
  cannot run fails"):
  - arguments: not exactly `<expected.json>`, `default=…`, `consent=…` (each label
    once) → exit 2;
  - `BROWSER_TESTS_BLOCKING_FROM` unset, not `YYYY-MM-DD`, or not a real date;
  - `expected.json` or a report missing, empty, or not JSON; a report with no
    `suites` array; a report whose top-level `errors` is not empty (for example the
    web server did not start);
  - the two reports list different test ids, or fewer than `minimumTests` distinct
    ids (a `.only`, a deleted test);
  - a test skipped that the build's expectation does not list (`test.skip`,
    `test.fixme`, or a consent build that lost its banner, which skips all 25);
  - a test the expectation lists as skipped that did **not** skip (a default build
    with a banner).
- **Test failures** (a test with status `unexpected` or `flaky`, or any
  `results[].status` other than `passed`/`skipped`): before
  `BROWSER_TESTS_BLOCKING_FROM` (UTC date, `new Date().toISOString().slice(0, 10)`)
  print each as `failed: <build>: <id>`, then
  `::warning title=Browser tests (report mode until <date>)::<n> failure(s)`, exit 0;
  on or after that date `::error …`, exit 1. `flaky` counts as a failure: retries
  are 0 today, and adding retries must not hide a failure.
- **Pass:** prints `browser suite: 29 tests; default 4 passed, 25 skipped as
  expected; consent 28 passed, 1 skipped as expected; 0 failures`.

No date override exists for tests; tests use `2000-01-01` (blocking) and
`2999-12-31` (report mode), and today's UTC date for the boundary.

### 3.2 Why each part

- **Exact expectation, not "exit 0".** Without it the job could go green with 4 of
  29 tests (2.1). The minimum count only rises (baselines only shrink); a new test
  raises it in its own pull request.
- **One job, two builds in sequence.** "All 29" needs both reports in one place.
- **Unchanged tests and config.** Nothing in `browser-tests/` or
  `playwright.config.ts` changes, so the suite CI runs is the suite developers run.

### 3.3 Report week

A new gate (standard section 3; no existing protection is replaced, the suite runs
nowhere today). The developer sets `BROWSER_TESTS_BLOCKING_FROM` to the planned
merge date plus seven days (`"2026-11-11"` for a 4 November merge). If the merge
moves, the date moves in the same pull request before merge: never fewer than seven
days after the merge, and never after `2026-11-23` (Wave 1's blocking date). If
the merge slips past 16 November so both cannot hold, the developer stops and the
change goes back to the owner; this plan does not decide it. Tech-lead
gate 2 checks the date against the merge date.

### 3.4 Canary (GAP-21, Wave 1-3 checklist)

`website/tools/browser-suite/canary/` holds three committed reports, reduced from
the real Playwright 1.56.1 JSON produced on `6470fac` in this session (absolute
paths and `config` stripped; only `suites`, `errors`, `stats` kept):

- `default.json`: the default run, every test as expected (4 passed, 25 skipped).
- `consent-failed.json`: the consent run with test 26 `failed` and its real error
  ("gsap is not defined"), the rest as expected.
- `consent-lost.json`: the consent build without its banner: all 25
  `consent.spec.ts` tests skipped and `pages.spec.ts:61` passed (the real default
  run's statuses under the `consent` label).

`website/tools/browser-suite/run-canary.mjs` spawns `check-report.mjs` as a child
process (no shared code path, no arguments that change behaviour) twice and exits 0
only when:

1. `BROWSER_TESTS_BLOCKING_FROM=2000-01-01`, `default.json` + `consent-failed.json`
   → exit 1 and output contains `failed: consent: pages.spec.ts › the skipped home
   intro moves the logo and its classes persist after load`;
2. `BROWSER_TESTS_BLOCKING_FROM=2999-12-31` (report mode), `default.json` +
   `consent-lost.json` → exit 1 and output names an unexpected skip in
   `consent.spec.ts`.

So loosening the checker to ignore failures, or to accept a lost consent build,
turns step 4 red on every pull request.

### 3.5 Alternatives rejected

- **Add steps to the existing `website` job.** It would be blocking at once (the
  job has no report mode), slower to read, and would touch the job that feeds
  `section-compare` (GAP-05's area). A separate job also gives a separate check
  name for branch protection.
- **A matrix of two jobs (default, consent).** Each job sees only part of the 29;
  a third aggregating job with artifact passing would be needed. More moving parts
  for no gain.
- **Reuse the `website-out` artifact for the default build.** Saves one build but
  adds `needs: website`, so a typecheck failure would show this job as skipped
  rather than run; and it would couple the gate to the section-compare artifact.
- **Rely on Playwright's exit code.** Passes with skipped tests (2.1).
- **`continue-on-error: true` for the report week.** It is the pattern GAP-05
  removes; it would also hide a gate that cannot run.
- **Add retries.** Would hide flaky failures; P-6.
- **Serve GSAP locally in CI or mock the CDN in the tests.** Changes the tests and
  the design lock; the CDN question is GAP-11's (SRI) and finding 8's fallback,
  outside this change.
